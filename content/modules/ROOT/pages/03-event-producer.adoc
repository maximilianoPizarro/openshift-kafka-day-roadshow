= Event Producer: Real Application

****
*Guiding question:* Who is writing the banking rows, and did your insert leave the database?
****

== Where we are

Kafka can hold a message. NeuralBank's application still only writes to PostgreSQL.

== Why it matters

If we must change the banking app to call Kafka, this project fails. The bank needs the email and the pipeline without editing that application.

== Concept

A separate Python simulator inserts customers, creates orders, and updates order status (about 40%, 40%, and 20%). PostgreSQL records those changes in its write-ahead log (WAL). Something between PostgreSQL and Kafka is copying the row. You will open that component in the Debezium CDC module. You are not looking at Debezium yet.

You are here: the simulator and PostgreSQL. The arrow to Kafka stays dashed until the Debezium module.

== Objectives

* Explore the CDC Data Simulator
* Confirm PostgreSQL is accepting banking rows
* Insert a customer yourself and see a related message in Kafka

== The CDC Data Simulator

image::event-producer-flow.jpg[Event Producer CDC Data Simulator flow,width=100%]

The simulator randomly performs:

* **40%** -- Insert a new customer
* **40%** -- Create a new order for an existing customer
* **20%** -- Update the status of an existing order

=== View Simulator Logs

Read the recent simulator output (do not use `-f`; the simulator only writes about once per minute):

[source,bash,role="execute"]
----
oc logs deployment/cdc-data-simulator -n kafka-cdc --tail=20
----

.Expected simulator Deployment (reference, not a step)
[source,yaml]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cdc-data-simulator
  namespace: kafka-cdc
spec:
  replicas: 1
  template:
    spec:
      containers:
        - name: simulator
          env:
            - name: PGHOST
              value: cdc-postgresql
            - name: PGDATABASE
              value: cdcdb
            - name: INTERVAL_SECONDS
              value: "60"
----

== Explore the PostgreSQL Database

Connect to the database and query the tables:

[source,bash,role="execute"]
----
oc exec -it deployment/cdc-postgresql -n kafka-cdc -- \
  psql -U cdcuser -d cdcdb -c "SELECT count(*) as total_customers FROM customers;"
----

[source,bash,role="execute"]
----
oc exec -it deployment/cdc-postgresql -n kafka-cdc -- \
  psql -U cdcuser -d cdcdb -c "SELECT * FROM orders ORDER BY id DESC LIMIT 5;"
----

=== Check WAL Configuration

Verify that PostgreSQL has logical WAL replication enabled. This setting lets a CDC tool read the change stream later:

[source,bash,role="execute"]
----
oc exec -it deployment/cdc-postgresql -n kafka-cdc -- \
  psql -U cdcuser -d cdcdb -c "SHOW wal_level;"
----

Expected output: `logical`

[source,bash,role="execute"]
----
oc exec -it deployment/cdc-postgresql -n kafka-cdc -- \
  psql -U cdcuser -d cdcdb -c "SELECT * FROM pg_publication;"
----

== Generate Your Own Events

Insert a customer manually. Replace `User1` / `user1` with your assigned number if you want the email to be unique:

[source,bash,role="execute"]
----
oc exec -it deployment/cdc-postgresql -n kafka-cdc -- \
  psql -U cdcuser -d cdcdb -c \
  "INSERT INTO customers (first_name, last_name, email) VALUES ('Workshop', 'User1', 'workshop.user1@neuralbank.io');"
----

Open the *Kafka Console* tab and open `cdc.public.customers`. You should see a new message. The `op` value is a label; `c` means the row was inserted. The Debezium CDC module defines the full event shape.

== Checkpoint

* The simulator log shows a customer or an order
* `wal_level` is `logical`
* The Kafka Console shows a new record on `cdc.public.customers` after your INSERT
