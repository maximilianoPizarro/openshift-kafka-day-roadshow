= Camel and Apicurio Registry

****
*Guiding question:* How do we stop a bad row without stopping the pipeline?
****

== Where we are

Debezium can follow a new database column. NeuralBank still needs a separate contract: reject a customer event that is missing an email without stopping Camel or Debezium.

You are here: Apicurio Registry and Camel, with a side path to `camel.schema-errors`.

== Objectives

* See where a schema registry fits in the CDC pipeline
* Inspect Red Hat build of Apicurio Registry 3
* Read the Camel route that validates customer and order rows
* Publish one valid record and one invalid record

== The validation path

Debezium writes the PostgreSQL change to Kafka. Camel reads that event, loads the JSON Schema from Apicurio, and publishes a smaller record.

image::camel-apicurio-flow.jpg[Camel and Apicurio Registry validation flow,width=100%]

`camel.schema-check` is checked against the customer schema. Orders are checked from `cdc.public.orders`.

The registry stores its data in the Kafka topic `kafkasql-journal` on `cdc-cluster`. That topic keeps records forever. If it did not, Apicurio would refuse to start.

== Schemas

Open the *Registry* tab. The group is `workshop`. Open `customers-value`, then the *Contract* tab. The same contract, `neuralbank-cdc`, is also attached to `orders-value`.

|===
|Contract field |Value

|Status
|Stable

|Owner team
|`neuralbank-platform`

|Domain
|`banking`

|Classification
|`CONFIDENTIAL`

|Support
|`platform@neuralbank.io`

|Quality
|Completeness, compliance, and stability, each 100%
|===

The contract rules require a customer email that contains `@` and a dot, and an order amount that is not empty. Scroll to *Contract Rules* to read those expressions.

Download the contract:

[source,bash,role="execute",subs="+attributes"]
----
curl -sk {registry_url}/apis/registry/v3/groups/workshop/contracts/neuralbank-cdc
----

On the *Overview* tab, each artifact header shows a name, a description, and the labels `domain=neuralbank` and `table`. Version `2` is the JSON Schema. Every column has a description, and an example row sits at the top of the document.

`customers-value` is the NeuralBank customer row from `public.customers`:

|===
|Field |Required |Meaning

|`first_name`
|yes
|Given name

|`last_name`
|yes
|Family name

|`email`
|yes
|Contact address. Must contain `@` and a dot

|`id`
|no
|PostgreSQL primary key. Missing when you publish through the Bridge

|`phone`
|no
|Present only after the instructor adds the column

|`created_at`
|no
|Row timestamp from Debezium
|===

`orders-value` is the NeuralBank order row from `public.orders`:

|===
|Field |Required |Meaning

|`product`
|yes
|Banking product, such as Mortgage or Personal Loan

|`amount`
|yes
|Money as text, for example `15000.00`. Debezium emits decimals as strings

|`status`
|yes
|`pending`, `approved`, `reviewing`, or `rejected`

|`customer_id`
|yes
|Foreign key to `customers.id`

|`id`, `created_at`
|no
|Assigned by PostgreSQL
|===

Extra columns are allowed. A new database column does not make the row invalid.

Read the customer artifact header, then the latest schema:

[source,bash,role="execute",subs="+attributes"]
----
curl -sk {registry_url}/apis/registry/v3/groups/workshop/artifacts/customers-value
curl -sk {registry_url}/apis/registry/v3/groups/workshop/artifacts/customers-value/versions/2/content
----

The header lists `name`, `description`, and `labels`. The schema lists `title`, `description`, `examples`, and a `description` on every property.

Each artifact has a `BACKWARD` compatibility rule. A newer version must still accept data written with the previous version. This version adds descriptions and optional columns. It does not add required fields.

[source,bash,role="execute",subs="+attributes"]
----
curl -sk {registry_url}/apis/registry/v3/groups/workshop/artifacts/customers-value/rules/COMPATIBILITY
----

== Camel route

The route is Apache Camel YAML, mounted from a ConfigMap into the `cdc-camel-router` Deployment. Camel loads the schema from Apicurio when it validates a record. A record that does not match the schema is published to `camel.schema-errors` and the consumer continues.

For a Debezium event, the row is `payload.after` (the same envelope you saw in the Debezium module). A delete, where `after` is null, is an invalid record.

[source,bash,role="execute"]
----
oc get configmap cdc-camel-routes -n kafka-cdc -o yaml
----

.Expected schema-check route (reference, not a step)
[source,yaml]
----
- route:
    id: schema-check
    from:
      uri: "kafka:camel.schema-check"
      parameters:
        brokers: "cdc-cluster-kafka-bootstrap:9092"
        groupId: "camel-schema-check"
        autoOffsetReset: "earliest"
      steps:
        - setProperty:
            name: eventSource
            constant: bridge
        - setProperty:
            name: schemaArtifact
            constant: customers-value
        - unmarshal:
            json: {}
        - bean:
            ref: schemaGuard
            method: validateCustomer
        - to:
            uri: "kafka:camel.validated"
----

The ConfigMap also contains `cdc-customers` and `cdc-orders`. Those routes read `payload.after`, validate it, and write to `camel.public.customers` and `camel.public.orders`.

List the Camel topics:

[source,bash,role="execute"]
----
oc get kafkatopic -n kafka-cdc
----

You should see `camel.schema-check`, `camel.validated`, `camel.schema-errors`, `camel.public.customers`, and `camel.public.orders`.

== Publish a valid customer

All workshop users share these topics. The Camel Deployment is the only validator. Replace `user1` in the email with your assigned number:

[source,bash,role="execute",subs="+attributes"]
----
curl -sk -X POST {bridge_url}/topics/camel.schema-check \
  -H "Content-Type: application/vnd.kafka.json.v2+json" \
  -d '{"records":[{"value":{"first_name":"Workshop","last_name":"User","email":"workshop.user1@neuralbank.io"}}]}'
----

Your publish succeeded if the curl returned an `offsets` array.

Read one validated record. The consumer prints the oldest record, which may belong to another participant. Use it to confirm the shape (`"schema":"customers-value"` and `"source":"bridge"`), not to prove the message is yours:

[source,bash,role="execute",subs="+attributes"]
----
oc run camel-validated -i --rm \
  --image={kafka_cli_image} \
  --restart=Never \
  -n $(oc whoami)-workshop \
  -- bin/kafka-console-consumer.sh \
    --bootstrap-server cdc-cluster-kafka-bootstrap.kafka-cdc.svc:9092 \
    --topic camel.validated \
    --from-beginning \
    --max-messages 1
----

To find your own email, search the *Kafka Console* on `camel.validated` for the address you typed.

== Publish an invalid customer

This record has no `email`, so the schema rejects it.

[source,bash,role="execute",subs="+attributes"]
----
curl -sk -X POST {bridge_url}/topics/camel.schema-check \
  -H "Content-Type: application/vnd.kafka.json.v2+json" \
  -d '{"records":[{"value":{"first_name":"Schema","last_name":"Test"}}]}'
----

[source,bash,role="execute",subs="+attributes"]
----
oc run camel-errors -i --rm \
  --image={kafka_cli_image} \
  --restart=Never \
  -n $(oc whoami)-workshop \
  -- bin/kafka-console-consumer.sh \
    --bootstrap-server cdc-cluster-kafka-bootstrap.kafka-cdc.svc:9092 \
    --topic camel.schema-errors \
    --from-beginning \
    --max-messages 1
----

You should see a record on `camel.schema-errors`. Camel keeps running after the rejection.
